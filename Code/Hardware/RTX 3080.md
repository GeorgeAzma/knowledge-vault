### How It Works
- **Warp Scheduler** `x4` issues 1 instruction/cycle can issue FP32 + INT32 instructions at the same time
- **Register File** `nvcc` determines how many registers each thread needs 
     and hardware multiplies that by number of threads resident on the SM
     if kernel uses too many registers per thread, the SM can house fewer warps 
     `register pressure reduces occupancy` registers spill to local memory `L1` when the file is full
- **TMU** uses `L1` via TEX path with hardware interpolation, LOD computation, address clamp/wrap.
     optimized for 2D spatial locality, accessing texels close to each other is cheaper
- **Constant Memory** `64K` uses `constant cache` which is `8K/SM` but spread across multiple SMs
     when all `x32` threads in a warp read same address, constant cache serves it in a single broadcast
- **L2 / DRAM** 320-bit bus is divided into `x10 32-bit channels`
     each channel has its own L2 slice `(from x40 128K L2 slices)` and its own DRAM chip
     128-byte
- **XBAR** connects all `L1s` to `L2`

### Claude Notes
#### Streaming Multiprocessor — the real unit of compute

The SM is the fundamental building block. Think of the GPU as a factory with 68 identical workstations (SMs), each capable of running completely independent work. The "clockspeed" you benchmark is per-SM. When CUDA launches a kernel, it divides work into thread blocks (CTAs), and the hardware schedules those blocks onto free SMs. An SM can hold multiple blocks simultaneously as long as there's enough register file space and shared memory.

The 4-partition structure inside each SM matters for throughput. Each partition has one warp scheduler, one dispatch unit, 32 FP32 cores, 16 INT32 cores, 1 Tensor Core, 1 SFU, 8 LSU ports. These sub-partitions operate in parallel, so a single SM can genuinely execute 4 independent warps per cycle.

**Occupancy** is the ratio of resident warps to maximum possible. Low occupancy means warps stall (on memory latency, for example) and there aren't enough other warps to hide the stall. The register file is usually the limiting resource: a kernel using 64 registers per thread can only house 4096 threads per SM (256 KB / (64 × 4 bytes)), which is 128 warps — well below the 192 max. Lowering register usage (via `__launch_bounds__` or `maxrregcount`) lets you pack more warps, improving latency hiding.

---

#### Register file and the spill hazard

The 256 KB register file is physically banked — accessing the same bank from two different warps in the same cycle causes a conflict stall. Registers are the fastest storage on the chip, with sub-cycle access when there's no bank conflict. When a kernel overflows its register budget, the compiler automatically inserts spill loads and stores to _local memory_, which is a per-thread region in global address space that the L1 will try to cache. Spills are extremely expensive — a spill to global memory is ~500 cycle latency if it misses L1.

---

#### The L1/Texture/Shared memory unification

Ampere merged three previously separate structures into one 128 KB SRAM per SM. At kernel launch you choose the split: up to 100 KB can be dedicated as shared memory, with the remainder as L1/texture cache. The compiler or programmer selects this via `cudaFuncSetAttribute(kernel, cudaFuncAttributeMaxDynamicSharedMemorySize, ...)`.

The _texture path_ within L1 is special: it has hardware units for bilinear/trilinear interpolation, S3TC decompression, LOD selection, and address wrapping/clamping — all in silicon. When you use `tex2D<float4>()`, the request routes through TMUs that perform these operations before the result hits your register. This is why texture sampling is "free" on the filtering side — the filtering hardware runs in parallel with execution.

---

#### L2 crossbar and the XBAR

Between SMs and L2 sits the **crossbar (XBAR)** — a high-bandwidth interconnect that routes traffic between any SM's L1 and any L2 slice. It's the reason `l1tex2xbar` and `xbar2lts` are separate metrics: the crossbar is a real physical bottleneck. On Ampere, the crossbar has ~40 ports on the SM side and 10 on the L2 side. When many SMs miss simultaneously, they can saturate the crossbar itself, which shows up as high `M_L1tex2xbar_req_cycles_active` alongside normal DRAM activity.

---

#### Wavefronts vs warps

In NVIDIA profiling terminology, a **wavefront** is not the same as a warp. A wavefront is a single cache line request generated by a warp. When 32 threads in a warp access memory, the hardware coalesces those accesses into as few cache line requests as possible. If all 32 threads touch addresses in the same 128-byte block → 1 wavefront. If they scatter across 32 different cache lines → 32 wavefronts. This is why the _wavefront_ metrics are better indicators of effective bandwidth than raw instruction counts: one warp instruction can generate 1 or 32 wavefronts depending on access pattern.

---

#### DRAM architecture — why PAM4 changes the physics

Standard DDR uses NRZ: 0 V or 1.8 V. PAM4 uses 4 voltage levels (0, 0.6, 1.2, 1.8 V), encoding 2 bits per symbol. The catch is signal integrity: with only 0.6 V between levels instead of 1.8 V, the noise margin is much tighter. GDDR6X chips include sophisticated equalization and error correction circuitry to compensate. From the programmer's perspective, PAM4 just means you get 19 Gbps/pin instead of ~14 Gbps for GDDR6 — the tradeoff is that your RTX 3080 runs warmer under memory-bound loads than an RX 6800 XT does at similar workloads.

The **sector** granularity (32 bytes) you see in L2/DRAM metrics comes from a hardware optimization: when only part of a 128-byte cache line is needed, GDDR6X can respond with a partial burst. This shows up in Nsight as sector-level tracking rather than full-line tracking, which helps identify cases where you're fetching full lines but using only one sector (wasted DRAM bandwidth).

---

#### Reading the metrics together

The interactive table covers each metric individually, but the real signal comes from correlating them:

If you see **DRAM Cycles Active near 100%** and **L2 D Sectors Fill Device near 100%**, you have a classic streaming-memory-bound kernel — your working set exceeds the 5 MB L2 and you're hammering 760 GB/s of DRAM bandwidth. The fix is tiling: restructure access patterns so each data element is used multiple times before eviction.

If you see **high L2 Tag Requests** but **low DRAM Cycles Active**, your L2 hit rate is good — misses are being served from L2 itself. This is the happy middle ground for many compute kernels.

If **L2 D Atomic Input Cycles Active** is high, you have atomic contention — many threads competing to update the same addresses in L2. The solution is warp-level reduction first (`__reduce_add_sync`), then block-level reduction in shared memory, then one global atomic per block.

If **L2 D Sectors Fill Sysmem** is meaningful, unified/managed memory or peer GPU access is involved, and you're paying PCIe latency (~16 GB/s vs 760 GB/s) — a ~47× bandwidth penalty.
